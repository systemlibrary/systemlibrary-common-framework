Tutorial

Duration: 30 minutes

This tutorial guides you through the framework’s common startup and module patterns: configuration, logging, controllers, static files, API controllers, and caching.

Prerequisite

  1. Follow the installation steps for the project.
  2. Ensure your app has an appsettings.json file with an application name:
{
  "systemLibraryCommonFramework": {
    "app": {
      "name": "company_unique_appname"
    }
  }
}

Chapter 1: Startup

The framework supports several startup approaches. The most flexible pattern is the direct host-builder extension API.

Extension API

Program.cs - fill in code:

using SystemLibrary.Common.Framework;
using SystemLibrary.Common.Framework.App;
using SystemLibrary.Common.Framework.App.Extensions;
using SystemLibrary.Common.Framework.Extensions;

var options = new FrameworkOptions();

var builder = Host.CreateDefaultBuilder(args);

builder.ConfigureFrameworkLogging();

builder.ConfigureServices((context, services) =>
{
    services = services.AddFrameworkServices(AppType.Web, options);
});

builder = builder.ConfigureWebHostDefaults(webBuilder =>
{
    webBuilder.ConfigureFrameworkHosting();

    webBuilder.Configure(app =>
    {
        app.UseFrameworkBeginMiddlewares(AppType.Web);
        app.UseFrameworkEndMiddlewares(AppType.Web);
    });
});

var app = builder.Build();
app.Run();

The framework also exposes Application.Start(...) and Application.Start<T>(...) helpers when you want the framework to manage the full host lifecycle for you.

Chapter 2: Configuration

The framework provides typed configuration through Config<T>. The config is loaded from files that match the type name and is cached after the first access.

Create configurations

~/Configs/PokemonConfig.json

{
  "url": "https://localhost:5010/api",
  "cacheDuration": 10
}

~/Configs/PokemonConfig.Development.json

{
  "url": "https://localhost:5010/api",
  "cacheDuration": 4
}

~/Configs/PokemonConfig.cs

public class PokemonConfig : Config<PokemonConfig>
{
    public string Url { get; set; }
    public int CacheDuration { get; set; }
}

Chapter 3: Controllers and views

Controllers can live alongside their views in feature folders and the framework will discover those paths automatically.

Create:

~/Content/Home/HomeController.cs

public class HomeController : Controller
{
    public IActionResult Index()
    {
        Log.Information("Home requested");
        return View();
    }
}

~/Content/Home/Index.cshtml

@model object

<h1>Home</h1>

The Home page is available at:

  • http://localhost:5010/
  • http://localhost:5010/Home

The Home controller is registered as the default homepage, so an empty Path routes to its Index action.

Chapter 4: Static files

Asset folders such as wwwroot, public, static, dist, frontend, assets, and files are served automatically.

Example, create an asset folder and place an image:

~/wwwroot/image.png

Then it is served as:

http://localhost:5010/image.png

Chapter 5: API controllers

API controllers inherit from BaseApiController, which adds JSON/XML response helpers.

public class PokemonApiController : BaseApiController
{
    public IActionResult Pikachu()
    {
        return Json(new { name = "Pikachu" });
    }
}

The framework adds route conventions and action matching based on controller names and namespaces.

Chapter 6: The client

Use the framework Client to execute outbound HTTP calls while reusing connection state and applying the framework’s retry behavior.

var client = new Client();
var response = client.Get<dynamic>(PokemonConfig.Current.Url + "/pokemon/pikachu");

Chapter 7: Cache

The framework cache is sharded and supports auto-generated keys, auth/admin skip rules, and conditional cache entries.

var name = Cache.Get("pokemon-pikachu", () =>
{
    var client = new Client();
    var response = client.Get<dynamic>(PokemonConfig.Current.Url + "/pokemon/pikachu");
    return response.Data?.name;
}, CacheDuration.M);

The generated key includes the calling context and user state when no explicit key is passed.
